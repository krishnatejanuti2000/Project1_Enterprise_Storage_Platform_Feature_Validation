# 1.2 — End-to-End Storage Data Path

## Objective

Understand how a storage I/O request travels from an application on the host through the operating system and storage stack, reaches the storage system and physical storage, and returns a completion/data response.

The learning abstraction used in this module is:

```text
Application
    ↓
Filesystem
    ↓
Operating System
    ↓
Block Layer
    ↓
Driver / Multipath
    ↓
Storage Protocol
    ↓
Storage Controller
    ↓
RAID / Pool
    ↓
Volume
    ↓
LUN
    ↓
Drive
```

> **Important:** The exact internal architecture and object relationships vary between storage products. The above sequence is a conceptual model for understanding the end-to-end path, not a claim that every vendor implements these objects as a literal linear chain.

---

# 1. Application Layer

The application operates at the file/data level.

For a normal file-based write, the application is concerned with:

* file
* file descriptor
* offset
* length
* data buffer

Conceptually:

```text
Application
    ↓
write(fd, buffer, length)
```

Example:

```text
File      = /data/test.bin
Offset    = 4096
Length    = 8192 bytes
Data      = application data
```

The application normally does **not** need to know:

```text
Filesystem blocks
Host LBA
LUN
RAID
Storage Pool
Physical Drive
```

### Important distinction

```text
File offset
≠
Filesystem block
≠
Host-visible LBA
≠
Physical drive location
```

For normal buffered I/O, the Linux page cache can participate in the write path. A call such as `fsync()` can be used when an application needs stronger persistence guarantees.

---

# 2. Filesystem Layer

The filesystem converts the application's file-level operation into storage operations.

Its responsibilities include maintaining the relationship between:

```text
File
  ↓
File offset
  ↓
Filesystem storage blocks / extents
```

The filesystem prepares block I/O for the kernel storage stack.

It does **not** simply assign a physical drive location directly.

Conceptually:

```text
Application
    ↓
Filesystem
    ↓
Filesystem mapping
    ↓
Block I/O
```

### Important distinction

The filesystem understands files and filesystem layout.

It does not normally need to understand:

```text
RAID layout
Physical SSD location
Array controller internals
```

---

# 3. Operating System Layer

The operating system/kernel coordinates the storage path.

In Linux, the filesystem, block layer, device drivers, and other storage components operate together inside the kernel.

For this roadmap, the important view is:

```text
Application
    ↓
Filesystem
    ↓
Linux kernel storage stack
```

The OS provides the mechanisms that allow application I/O to reach the appropriate block device and eventually return completion information.

---

# 4. Block Layer

The Linux block layer provides the generic block-I/O infrastructure between filesystems and device-specific storage drivers.

A simplified flow is:

```text
Filesystem
    ↓
BIO
    ↓
Block Layer
    ↓
struct request
    ↓
blk-mq
    ↓
Driver
```

## BIO

A `bio` describes block I/O and contains information about the operation and the data segments involved.

A BIO is **not simply one large buffer**.

Multiple compatible BIOs may be merged by the block layer.

Merging is possible but is not guaranteed for every I/O.

## Request

The block layer can build a `struct request` from one or more BIOs.

Conceptually:

```text
BIO
 ↓
Block Layer
 ↓
Request
 ↓
blk-mq
```

The request is then dispatched toward the appropriate storage driver.

### Important correction

The original BIO should not be described as simply "going directly to the driver."

A more accurate simplified model is:

```text
Filesystem
→ BIO
→ Block Layer
→ Request
→ blk-mq
→ Driver
```

---

# 5. Driver / Multipath

The driver is the device/protocol-specific component that handles the lower-level operation required by the storage architecture.

There is no single universal "storage driver."

Examples include:

```text
Local SATA/SAS
    → corresponding storage/device drivers

NVMe
    → NVMe driver

SAN
    → SCSI stack + transport/HBA-related components
```

## Driver role

The driver handles things such as:

* converting the generic request into a device/protocol-specific operation
* submitting the operation
* receiving completion
* handling device/path errors

## Multipath

When multiple storage paths exist, a multipath layer can represent those paths as one logical device.

Conceptually:

```text
              ┌── Path 1 ──→ Storage
Host
              ├── Path 2 ──→ Storage
              └── Path 3 ──→ Storage
                    ↓
              Multipath device
```

For example:

```text
/dev/mapper/mpatha
```

may represent multiple underlying paths.

Multipath selects an eligible path according to its state and configured policy.

### Important point

Multipath is not required for every storage architecture.

---

# 6. Storage Protocol

The storage protocol provides the rules/mechanisms used to communicate the storage operation between the host side and storage target.

Important distinctions:

```text
SCSI
= storage command model / command architecture

FC
= Fibre Channel transport/fabric technology

iSCSI
= carries SCSI commands over TCP/IP

SAS
= commonly transports SCSI commands over SAS
```

For example, a conceptual host request can be represented as:

```text
LUN 10
WRITE
LBA 1000
Length = 8 blocks
```

The host-visible LUN identifies the logical storage unit, while the LBA identifies a logical block within that address space.

Detailed SCSI commands, FC behavior, iSCSI sessions, and SAS internals are covered later in their dedicated modules.

---

# 7. Storage Controller

The storage controller is the array-side processing/control component that receives host I/O and handles it according to the array's configured storage architecture.

Conceptually:

```text
Host
  ↓
Storage Protocol
  ↓
Array Front-End
  ↓
Controller
```

Suppose the host sends:

```text
LUN 10
WRITE
LBA 1000
Length = N blocks
Data
```

The controller-side processing conceptually involves:

```text
Receive host request
        ↓
Determine/validate the logical storage target
        ↓
Apply configured access and logical-storage rules
        ↓
Process the request within the array architecture
        ↓
Coordinate the required backend operation
```

The controller may also participate in cache handling.

### Important point

Do not picture the controller as simply doing:

```text
LUN 10 / LBA 1000
        ↓
Drive 7
```

The array contains additional logical and protection layers between the host-visible request and the physical media.

### Vendor-specific behavior

Exactly how the controller performs:

* logical address translation
* caching
* scheduling
* backend mapping
* failover
* metadata handling

depends on the storage platform.

Those details must not be treated as universal.

---

# 8. RAID / Storage Pool

Once the array has accepted the logical request, the underlying storage organization determines how that data is represented on physical storage.

## RAID

RAID defines a protection/layout scheme for a set of physical drives.

Examples:

```text
RAID 0
RAID 1
RAID 5
RAID 6
RAID 10
```

Conceptually:

```text
Logical data
      ↓
RAID layout/protection
      ↓
Data and/or mirror/parity operations
      ↓
Multiple physical drives
```

For a parity RAID configuration, a write may require data and parity-related backend operations.

For a mirrored configuration, copies of the data may be maintained.

The exact implementation depends on the RAID design.

---

## Storage Pool

A storage pool is a logical collection of managed storage capacity from which logical storage resources can be allocated.

Conceptually:

```text
Physical storage
      ↓
Protection / storage organization
      ↓
Storage Pool
      ↓
Allocatable logical capacity
```

The useful distinction is:

```text
RAID
= how underlying storage is protected/organized

Pool
= managed capacity resource used for logical allocation
```

RAID and Pool are therefore different concepts even though a particular product may implement them together or expose them differently.

---

# 9. Volume

A volume is an array-side logical storage object allocated from the storage system's underlying capacity resources.

Conceptually:

```text
Storage Pool
      ↓
   Volume
```

Example:

```text
Storage Pool
    ↓
Volume A — 500 GB
```

A volume is still an array-side logical object.

It is not a physical disk.

---

# 10. LUN

A LUN is a logical storage unit presented to a host in a SCSI-based block-storage environment.

Conceptually:

```text
Array-side logical storage
          ↓
         LUN
          ↓
         Host
```

Example:

```text
LUN 10
```

The host can issue block operations against that logical storage unit using logical block addresses.

Example:

```text
LUN 10
LBA 1000
WRITE
```

### Important distinction

```text
Volume
= array-side logical storage object

LUN
= host-presented logical block storage unit
```

These are related concepts but are not universally identical objects across all storage products.

---

# 11. Drive

The drive is the physical storage device that ultimately stores or retrieves the data.

Examples:

```text
HDD
SSD
NVMe SSD
```

The array's internal processing determines the backend drive operations required.

Conceptually:

```text
Logical host request
       ↓
Array processing
       ↓
Internal storage mapping
       ↓
Backend drive operation
       ↓
Physical storage media
```

The physical drive does not receive the original host-level concept of:

```text
LUN 10 / LBA 1000
```

The array has already processed that logical request before the backend operation reaches the drive.

---

# 12. Complete WRITE Path

Consider:

```text
WRITE
LUN 10
LBA 1000
Length = N blocks
Data
```

A simplified end-to-end flow is:

```text
Application
    ↓
Filesystem
    ↓
Linux kernel / OS
    ↓
BIO
    ↓
Block Layer
    ↓
struct request
    ↓
blk-mq
    ↓
Driver / Multipath
    ↓
Storage Protocol
    ↓
Array Front-End
    ↓
Storage Controller
    ↓
Array logical-storage processing
    ↓
RAID / Pool organization
    ↓
Volume / LUN relationship
    ↓
Backend mapping
    ↓
Physical Drive
```

The physical drive stores the required data according to the array's internal architecture.

---

# 13. Complete READ Path

Now consider:

```text
READ
LUN 10
LBA 1000
Length = N blocks
```

Conceptually:

```text
Application
    ↓
Filesystem
    ↓
Linux kernel / OS
    ↓
Block Layer
    ↓
Driver / Multipath
    ↓
Storage Protocol
    ↓
Array Front-End
    ↓
Storage Controller
    ↓
Array logical-storage processing
    ↓
RAID / Pool organization
    ↓
Backend mapping
    ↓
Physical Drive
    ↓
Data returned
    ↓
Controller
    ↓
Protocol / host path
    ↓
Driver
    ↓
Block Layer
    ↓
Filesystem
    ↓
Application
```

The READ direction therefore traverses the same major storage layers, with the data flowing back toward the application after the backend storage operation completes.

---

# 14. Critical Logical vs Physical Distinction

One of the most important concepts in 1.2 is:

```text
File
    ↓
Filesystem representation
    ↓
Host logical block
    ↓
LUN
    ↓
Array logical mapping
    ↓
RAID / Pool organization
    ↓
Physical storage
```

Therefore:

```text
File offset
≠
Filesystem block
≠
Host LBA
≠
LUN
≠
Physical drive location
```

Each layer has its own abstraction.

# 15. Troubleshooting / RCA View

During a real storage-validation failure, do not immediately call the problem a "storage issue."

Determine which layer is failing.

Examples:

### Application / Filesystem

```text
Application cannot read/write a file
```

Possible investigation area:

```text
Application
Filesystem
Mount
Permissions
Filesystem errors
```

### Block Layer

```text
I/O is generated but fails before reaching the expected device
```

Investigate:

```text
Block device
Block layer
Kernel messages
Device state
```

### Driver / Path

```text
One storage path disappears
```

Investigate:

```text
Driver
HBA/NIC
Transport
Path state
Multipath
```

### Protocol / Connectivity

```text
Host cannot communicate with the storage target
```

Investigate:

```text
Protocol
Transport
Fabric/network
Target connectivity
```

### Controller

```text
Host can reach the array but I/O processing fails
```

Investigate:

```text
Controller state
Controller logs
Controller ownership/failover
Array health
```

### RAID / Backend Storage

```text
LUN is accessible but backend protection/storage reports degradation
```

Investigate:

```text
RAID state
Pool state
Drive health
Rebuild state
Backend errors
```

This layer-oriented approach is the foundation of storage troubleshooting and RCA.

# 16. Real-World Validation Perspective

In a company storage-validation environment, an engineer should be able to reason through the complete path:

```text
Requirement
    ↓
Host + Storage Environment
    ↓
Platform Ready
    ↓
Provisioned Storage
    ↓
Host Presentation
    ↓
Application / FIO I/O
    ↓
Storage Stack
    ↓
Array Processing
    ↓
Backend Storage
    ↓
Result
    ↓
Failure / Recovery if injected
    ↓
Evidence
    ↓
RCA
```

The purpose of learning 1.2 is not to memorize names.

The purpose is to understand:

> **Where an I/O originates, how each layer transforms or carries it, where it becomes a logical storage operation, where it reaches physical storage, and how a failure at one layer affects the rest of the path.**

---

# 17. What Is Universal vs Vendor-Specific?

## Broadly universal concepts

```text
Application
Filesystem
Host OS
Block I/O
Device driver
Storage communication
Logical storage
Physical storage
```

## Product-dependent implementation

```text
Exact controller architecture
Exact RAID implementation
Pool implementation
Volume implementation
LUN mapping model
Cache architecture
Internal logical-to-physical mapping
Backend scheduling
Failover behavior
```

Therefore, during validation we must always ask:

> **Is this a universal storage concept, or an implementation detail of this particular platform?**
