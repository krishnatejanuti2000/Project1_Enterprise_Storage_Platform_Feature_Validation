# Module 01 — Enterprise Storage Architecture

## 1.1 Storage Models — DAS, SAN and NAS

---

# 1.1.1 Overview

A storage model describes **how storage is connected to a host/client and how storage is presented for use**.

The three foundational storage models are:

1. **DAS — Direct-Attached Storage**
2. **SAN — Storage Area Network**
3. **NAS — Network Attached Storage**

The most important distinction is:

```text
DAS → Direct attachment
SAN → Block-level storage over a storage network
NAS → File-level storage over a network
```

---

# 1.1.2 DAS — Direct-Attached Storage

## Definition

**DAS (Direct-Attached Storage)** is storage that is directly connected to a host without a storage network or fabric between the host and the storage.

The defining characteristic is **direct attachment**.

It should not be defined as "storage that can only be accessed by one host." Single-host usage is common, but it is not what defines DAS.

---

## DAS Topology

### Basic topology

```text
┌──────────────┐
│     Host     │
│   / Server   │
└──────┬───────┘
       │
       │ Direct Storage Connection
       │
┌──────▼───────┐
│    Storage   │
│  Drive /     │
│  Enclosure   │
└──────────────┘
```

The host communicates with the storage through a direct storage connection.

Examples include:

```text
Host ── SATA ── SSD/HDD
Host ── SAS  ── Storage Enclosure
Host ── PCIe ── NVMe SSD
Host ── USB  ── Storage Device
```

The exact interface can vary; what matters here is that the storage is **directly attached to the host**.

---

## How DAS Works

A simplified host-side path is:

```text
Application
    ↓
Filesystem
    ↓
Operating System
    ↓
Block Layer
    ↓
Storage Driver
    ↓
Direct Storage Connection
    ↓
Storage Device
```

The host generally manages the block device and filesystem when using block storage.

For example:

```text
Linux Host
     ↓
/dev/nvme0n1
     ↓
Filesystem
     ↓
/data
```

---

## Advantages of DAS

Because the architecture is direct:

### 1. Simple architecture

```text
Host ───────── Storage
```

There is no dedicated storage fabric in a basic DAS configuration.

### 2. Lower infrastructure complexity

A basic DAS environment does not require SAN switches or a dedicated storage network.

### 3. Direct communication path

The host communicates directly with the attached storage, giving a relatively straightforward I/O path.

### 4. Lower infrastructure cost

For smaller deployments, DAS can avoid the additional infrastructure required by a SAN.

### 5. Easy to deploy for local workloads

DAS is well suited when storage is closely associated with a particular server or system.

---

## Disadvantages of DAS

### 1. Limited storage sharing

DAS is not primarily designed as a shared enterprise storage architecture.

### 2. Scaling can become difficult

As the number of servers and storage requirements increase, attaching and managing storage independently can become more difficult.

### 3. Storage utilization can be less flexible

Capacity attached to one server may not be easily redistributed to another server.

### 4. Availability depends on the design

A failed direct connection or storage component can affect the host's access to that storage.

### 5. Centralized enterprise management is limited

Large environments often require centralized provisioning, monitoring, access control, and storage management.

---

## DAS Key Characteristics

```text
Connection:
Directly attached

Storage network/fabric:
Not required for the core architecture

Primary consumer:
Host

Typical examples:
SATA
SAS
PCIe / NVMe
USB

Typical use:
Local or directly attached storage
```

---

## DAS Real-World Example

A server contains an NVMe SSD:

```text
Server
  │
  └── PCIe
        │
     NVMe SSD
```

The Linux operating system detects the device:

```text
/dev/nvme0n1
```

The host can partition it, create a filesystem, mount it, and use it.

---

## DAS Common Misconception

### Incorrect

> DAS means only one host can access the storage.

### Correct

> **DAS means the storage is directly attached to the host.**

The number of hosts is not the defining characteristic.

---

## DAS Interview Answer

> **DAS, or Direct-Attached Storage, is storage that is directly connected to a host without a storage network or fabric between the host and the storage.**

---

# 1.1.3 SAN — Storage Area Network

## Definition

**SAN (Storage Area Network)** is a dedicated storage networking architecture that provides hosts with **block-level access to storage resources**.

The two concepts to remember are:

```text
Storage networking
        +
Block-level access
```

---

## SAN Topology

### Basic topology

```text
┌──────────────┐
│    Server    │
└──────┬───────┘
       │
      HBA
       │
       ▼
┌─────────────────┐
│   SAN Fabric    │
│                 │
│ SAN Switch /    │
│ Fabric          │
└────────┬────────┘
         │
         ▼
┌──────────────────────┐
│    Storage Array     │
│                      │
│ Controllers          │
│ Cache                │
│ RAID / Pool           │
│ Volumes / LUNs        │
└──────────┬───────────┘
           │
           ▼
        Drives
```

A common enterprise path is:

```text
Host
  ↓
HBA
  ↓
SAN Fabric
  ↓
Storage Controller
  ↓
Storage Resource
  ↓
Drives
```

---

## Important: SAN vs SAN Switch

A SAN switch is **not the SAN itself**.

```text
SAN
│
├── Hosts / HBAs
├── SAN Fabric
├── Switches
├── Storage connectivity
├── Storage systems
└── Storage resources
```

Therefore:

```text
SAN ≠ SAN Switch
```

A SAN switch provides connectivity within the SAN fabric between hosts and storage systems.

---

## How SAN Works

The storage system presents block storage to the host.

A simplified flow is:

```text
Storage Array
     ↓
LUN / Block Storage
     ↓
SAN Fabric
     ↓
Host
     ↓
Block Device
     ↓
Filesystem
     ↓
Application
```

For example:

```text
Storage Array
     ↓
LUN
     ↓
SAN
     ↓
Linux
     ↓
/dev/sdb
     ↓
Filesystem
     ↓
/data
```

The important concept is:

> **The host receives block-level storage and manages the filesystem on that block storage.**

---

## SAN Protocol Examples

Common block-storage networking technologies include:

```text
Fibre Channel (FC)
iSCSI
```

These provide different mechanisms for delivering block storage to the host.

---

## Advantages of SAN

### 1. Centralized storage

Storage can be provided from centralized enterprise storage systems.

### 2. Shared storage

Multiple hosts can access centralized storage resources according to the configured access controls and storage mappings.

### 3. Scalability

SAN architectures can support many hosts and large amounts of storage.

### 4. High availability

Enterprise SAN designs can introduce redundancy across:

```text
Host paths
HBAs
SAN fabrics
Switches
Storage ports
Controllers
```

### 5. Flexible provisioning

Storage resources can be allocated and presented to hosts according to application requirements.

### 6. Suitable for enterprise block-storage workloads

SAN is commonly used where centralized block storage and high availability are required.

---

## Disadvantages of SAN

### 1. Higher architectural complexity

A SAN may involve:

```text
HBA
Switches
Fabric
Zoning
Storage controllers
LUNs
Multipathing
Access control
```

### 2. Higher infrastructure cost

SAN infrastructure can require dedicated switches, HBAs, optics, cabling, storage systems, and supporting components.

### 3. More complex troubleshooting

A storage-access problem can originate from several layers:

```text
Host
 ↓
HBA
 ↓
Driver
 ↓
Fabric
 ↓
Switch
 ↓
Storage Port
 ↓
Controller
 ↓
LUN
 ↓
Backend Storage
```

### 4. Configuration errors can affect access

Incorrect zoning, masking/mapping, multipathing, or host configuration can prevent storage access.

---

## SAN Key Characteristics

```text
Architecture:
Storage networking

Access:
Block-level

Typical host component:
HBA

Typical technologies:
FC
iSCSI

Filesystem ownership:
Typically host

Typical storage object:
LUN

Typical use:
Enterprise block storage
```

---

## SAN Real-World Example

Suppose a Linux server requires 2 TB of shared enterprise storage.

A simplified setup might be:

```text
Linux Server
     ↓
FC HBA
     ↓
FC SAN Fabric
     ↓
Storage Array
     ↓
2 TB LUN
     ↓
Linux sees block device
     ↓
Filesystem
     ↓
Application
```

The storage array owns the underlying physical storage architecture.

The host receives the presented block storage.

---

## SAN Common Misconceptions

### Incorrect

> SAN means SAN switch.

### Correct

> **SAN is the overall storage networking architecture. A SAN switch is one component within that architecture.**

---

### Incorrect

> SAN gives the host files directly.

### Correct

> **SAN provides block-level storage. The host can then create/manage a filesystem on the block device.**

---

## SAN Interview Answer

> **SAN, or Storage Area Network, is a dedicated storage networking architecture that provides hosts with block-level access to storage resources.**

# 1.1.4 NAS — Network Attached Storage

## Definition

**NAS (Network Attached Storage)** is a storage system connected to a network that provides clients with **file-level access to data**.

Remember:

```text
NAS = Network Attached Storage
```

Not:

```text
Network Area Storage
```

---

## NAS Topology

```text
┌──────────────┐
│    Client    │
│   / Server   │
└──────┬───────┘
       │
       │ IP Network
       │
       ▼
┌────────────────────┐
│        NAS         │
│                    │
│ NAS Software       │
│ Filesystem         │
│ RAID / Pool        │
│ Drives              │
└────────────────────┘
```

A typical access path is:

```text
Client
  ↓
Ethernet / IP Network
  ↓
NAS
  ↓
Files / Directories
```

---

## How NAS Works

The client accesses file services from the NAS.

Common protocols include:

```text
NFS
SMB / CIFS
```

Conceptually:

```text
Client
  ↓
NFS / SMB
  ↓
NAS
  ↓
Files / Directories
```

The client normally does not receive the NAS system's raw underlying block storage.

---

## NAS Internal Architecture

A NAS system can internally contain:

```text
Drives
   ↓
RAID / Pool
   ↓
Filesystem
   ↓
NAS Software
   ↓
Files
```

Therefore:

> **NAS can use block-level storage internally while still providing file-level access to clients.**

The distinction is based on the **interface presented to the client**, not on whether blocks exist internally.

---

## Advantages of NAS

### 1. Simple file sharing

Multiple clients can access shared files through network file-sharing protocols.

### 2. Centralized file storage

Files can be managed from a centralized storage system.

### 3. Easier file-level access

Clients can work with:

```text
Files
Directories
Shares
Permissions
```

without managing the underlying storage blocks.

### 4. Centralized management

Storage administrators can manage shared filesystems and storage resources centrally.

### 5. Suitable for shared file workloads

NAS is useful for workloads that require shared file access rather than raw block storage.

---

## Disadvantages of NAS

### 1. Network dependency

Client access depends on network connectivity.

```text
Client
  ↓
Network
  ↓
NAS
```

A network problem can interrupt file access.

### 2. Network performance can become a factor

Performance depends not only on the storage system but also on aspects of the network path.

### 3. File-level interface limitations

NAS provides file-level access rather than exposing raw block storage to the client.

### 4. Shared-resource contention

Multiple clients may compete for the same NAS resources depending on the workload and system design.

### 5. Troubleshooting crosses multiple layers

A file-access problem may involve:

```text
Client
 ↓
Network
 ↓
NAS protocol
 ↓
NAS filesystem
 ↓
NAS storage system
 ↓
Backend storage
```

---

## NAS Key Characteristics

```text
Architecture:
Network attached

Access:
File-level

Typical protocols:
NFS
SMB / CIFS

Filesystem ownership:
NAS system

Typical consumer:
Client

Typical use:
Shared file storage
```

---

## NAS Real-World Example

Suppose a company needs a shared location for project documents.

The architecture could be:

```text
Employee PC
     ↓
Ethernet
     ↓
IP Network
     ↓
NAS
     ↓
Shared Filesystem
     ↓
Project Documents
```

The employee interacts with:

```text
Folders
Files
Shares
```

rather than receiving a raw block device from the NAS.

---

## NAS Common Misconceptions

### Incorrect

> NAS does not use blocks internally.

### Correct

> **NAS can internally use drives, blocks, RAID, pools, and filesystems. It presents file-level access to the client.**

---

### Incorrect

> NAS and SAN are the same because both use networking.

### Correct

```text
SAN → Block-level access
NAS → File-level access
```

---

## NAS Interview Answer

> **NAS, or Network Attached Storage, is a storage system connected to a network that provides clients with file-level access to data, typically through protocols such as NFS or SMB/CIFS.**

| Characteristic                  | DAS                             | SAN                      | NAS                           |
| ------------------------------- | ------------------------------- | ------------------------ | ----------------------------- |
| Full form                       | Direct-Attached Storage         | Storage Area Network     | Network Attached Storage      |
| Core architecture               | Direct attachment               | Storage networking       | Network-attached file storage |
| Access presented                | Direct/local storage access     | Block-level              | File-level                    |
| Dedicated storage fabric        | Not required                    | Typically used           | Not a SAN fabric              |
| Typical technologies            | SATA, SAS, PCIe/NVMe, USB       | FC, iSCSI                | NFS, SMB/CIFS                 |
| Filesystem generally managed by | Host                            | Host                     | NAS system                    |
| Typical storage object          | Local block device              | LUN / block device       | File / directory              |
| Centralized storage             | Limited                         | Yes                      | Yes                           |
| Shared access model             | Limited/configuration dependent | Common                   | Common                        |
| Complexity                      | Lower                           | Higher                   | Moderate                      |
| Typical use                     | Local/direct storage            | Enterprise block storage | Shared file storage           |

# 1.1.7 The Critical Storage Principle

Do not confuse the **internal implementation of a storage system** with the **interface presented to the consumer**.

For example:

### SAN

Internally:

```text
Drives
 ↓
RAID / Pool
 ↓
Volumes
 ↓
LUN
```

Presented to host:

```text
Block Device
```

The host manages the filesystem.

---

### NAS

Internally:

```text
Drives
 ↓
RAID / Pool
 ↓
Filesystem
 ↓
Files
```

Presented to client:

```text
Files / Directories
```

The NAS system manages the filesystem.

Therefore:

```text
Internal implementation
        ≠
Consumer-facing storage interface
```

This distinction will become increasingly important when we study:

* Storage arrays
* Controllers
* RAID
* Pools
* Volumes
* LUNs
* SCSI
* SAS
* SATA
* SAN
* Multipathing
* Storage provisioning

## 1.1.4 Storage Array

### Definition

A **Storage Array** is a dedicated storage system that manages physical storage resources and provides logical storage resources to hosts.

The array abstracts the underlying physical drives and manages them as a storage system rather than exposing only individual physical devices.

### High-Level Topology

```text
                Hosts
                  │
                  ▼
          ┌─────────────────┐
          │  Storage Array  │
          │                 │
          │ Managed Storage │
          └────────┬────────┘
                   │
                   ▼
                 Drives
```

### What the Storage Array Provides

At a high level, an enterprise storage array can provide:

* Centralized storage management
* Logical storage allocation
* Data-protection mechanisms
* Storage sharing according to configured access controls
* Storage presentation to hosts
* Redundant components and paths, depending on architecture
* Monitoring and management capabilities

### High-Level Internal View

```text
Physical Drives
      ↓
Storage Management
      ↓
Logical Storage Resources
      ↓
Host Presentation
```

An enterprise array may contain components such as:

```text
Controllers
Cache
Front-end connectivity
Back-end connectivity
RAID / Protection
Storage Pools
Volumes
LUNs
Management Interfaces
Power
Cooling
```

These components are intentionally covered only at a **high level in 1.1**.

Their detailed operation belongs to:

```text
1.3 — Array Architecture
1.4 — Physical Components
```

### Why Storage Arrays Are Used

A dedicated storage system allows an enterprise to manage storage centrally instead of treating storage as isolated physical resources attached independently to individual systems.

This provides greater flexibility in:

* Capacity allocation
* Storage protection
* Host presentation
* Storage expansion
* Availability
* Operational management

### Important Principle

> **A healthy storage array is not automatically application-ready.**

The physical platform must first be ready, and logical storage must then be provisioned and presented to the intended host before applications can consume it.

# 1.1.5 JBOD — Just a Bunch of Disks

### Definition

**JBOD (Just a Bunch of Disks)** is a storage configuration in which multiple physical drives are provided as individual drives rather than being transformed by the JBOD enclosure itself into an intelligent logical storage system.

### Topology

```text
              Host
                │
                │
                ▼
         ┌──────────────┐
         │     JBOD     │
         │   Enclosure  │
         └──────┬───────┘
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
     Drive     Drive    Drive
       1         2        3
```

### How It Works

The JBOD enclosure primarily provides the physical infrastructure required to house and connect the drives.

The individual drives remain individually addressable.

```text
JBOD
  ↓
Individual physical drives
```

The JBOD itself does not inherently provide:

```text
RAID
Storage Pools
Volumes
LUN presentation
Array-level storage management
```

Those functions may be provided by another controller or storage-management layer.

### Advantages

* Simple physical architecture
* Provides multiple drives in one enclosure
* Allows individual-drive access
* Useful as additional storage behind another controller/system
* Can provide a scalable physical drive enclosure depending on platform design

### Disadvantages

* Does not inherently provide array-level data protection
* Does not inherently provide logical storage abstraction
* Storage management may have to occur at another layer
* Availability depends on the surrounding architecture

### Key Engineering Point

> **JBOD primarily provides access to individual physical drives; it is not, by itself, a complete intelligent storage array.**

---

# 1.1.6 Storage Enclosure

### Definition

A **Storage Enclosure** is a physical chassis that houses storage devices and provides the infrastructure required to integrate those devices into a larger storage system.

### Topology

```text
        STORAGE ENCLOSURE

┌──────────────────────────────┐
│                              │
│ Drive 1     Drive 2          │
│ Drive 3     Drive 4          │
│                              │
│ Backplane / Internal         │
│ Connectivity                │
│                              │
│ Power                        │
│ Cooling                      │
│                              │
└──────────────────────────────┘
```

### What the Enclosure Provides

Depending on its design, an enclosure can provide:

* Drive bays
* Drive mounting
* Backplane/internal connectivity
* External connectivity
* Power
* Cooling
* Physical expansion capability

### Advantages

* Centralizes physical drive installation
* Simplifies physical storage expansion
* Provides organized drive connectivity
* Supports serviceability and hardware replacement
* Can provide additional capacity to a larger storage system

### Disadvantages

* An enclosure by itself does not necessarily provide logical storage management
* Data protection depends on the surrounding controller/system
* Availability depends on enclosure and surrounding connectivity design

### Important Distinction

> **Enclosure describes the physical platform that houses the drives.**

The exact capabilities of an enclosure depend on its design and the system it belongs to.

# 1.1.7 All-Flash Array — AFA

### Definition

An **All-Flash Array (AFA)** is a storage array whose primary storage media is flash-based, typically SSDs.

### Topology

```text
             Storage Array
                  │
                  ▼
        Flash / SSD Storage
        ┌─────┬─────┬─────┐
        │ SSD │ SSD │ SSD │
        └─────┴─────┴─────┘
```

### What "All-Flash" Describes

The term primarily describes:

> **The storage media used by the array.**

It does not by itself define:

* Controller architecture
* RAID level
* Storage protocol
* Multipathing model
* Active/Active operation
* Active/Passive operation
* Provisioning method

Those are separate architectural properties.

### Why Enterprises Use AFA

Flash-based storage is commonly selected for workloads requiring low storage latency and high I/O performance.

Examples can include:

* Databases
* Virtualization
* Transaction-heavy applications
* Latency-sensitive workloads

Actual system performance depends on the complete storage architecture and workload, not simply on the fact that the array is all-flash.

### Advantages

* Low storage latency
* High I/O capability
* Strong performance for latency-sensitive workloads
* No mechanical seek operations associated with HDD media
* Good fit for high-performance enterprise workloads

### Disadvantages

* Typically higher media cost than HDD-based storage
* Performance and endurance depend on SSD characteristics and system design
* Does not automatically guarantee high availability or maximum performance

### Key Engineering Point

```text
AFA
 ↓
Describes storage media
```

It does **not** describe the entire storage architecture.

# 1.1.8 Controller-Based Storage

### Definition

**Controller-Based Storage** is a storage architecture in which a storage controller provides the processing and control layer between the host-facing side and the underlying storage resources.

### High-Level Topology

```text
Host
  │
  ▼
Controller
  │
  ▼
Managed Storage
  │
  ▼
Physical Storage
```

### What the Controller Provides

At a high level, the controller participates in:

* Storage I/O processing
* Storage-resource management
* Logical storage handling
* Host/storage connectivity
* Backend storage operations
* Storage-system control

The exact controller responsibilities depend on the platform.

### Advantages

* Provides storage-system-level control
* Enables logical storage abstraction
* Allows storage management above individual drives
* Can support data-protection mechanisms
* Can support redundant-controller designs depending on architecture

### Disadvantages

* Adds hardware and software complexity
* Controller failure can become a critical failure domain if redundancy is absent
* Controller behavior and capabilities vary by platform
* Requires proper configuration and monitoring

### Key Engineering Point

The important architectural distinction is:

```text
Physical Drives
      ↓
Controller
      ↓
Managed Storage
      ↓
Host
```

The controller therefore provides a **storage-processing and control layer**, rather than simply acting as a physical connection between a host and a drive.

Detailed controller behavior is covered in:

```text
1.3 — Array Architecture
```

# 1.1.9 Storage Exposure / Presentation — Supporting Concept

### Purpose

A storage system can contain physical capacity and logical storage resources, but a host cannot use a logical resource until that resource is **presented to the intended host**.

At a high level:

```text
Storage Resource
       ↓
Host Presentation
       ↓
Host
       ↓
Operating System
```

### Conceptual Flow

```text
Physical Storage
      ↓
RAID / Protection
      ↓
Pool
      ↓
Volume
      ↓
LUN / Logical Unit
      ↓
Host Mapping
      ↓
Host Discovery
```

This is the bridge between:

```text
Storage Array
```

and:

```text
Host
```

### Important Principle

Creating a storage resource does **not automatically mean the host can use it**.

There is a separate presentation/access-control stage.

For example, the storage system may need to associate the logical storage resource with the intended host identity.

The exact mechanism depends on the storage protocol and platform.

This concept becomes a major hands-on topic later in:

```text

```

where we will properly learn:

```text
LUN
Mapping
Masking
Host
Host Group
Initiator Identity
Host Discovery
Filesystem
Application Access
```
