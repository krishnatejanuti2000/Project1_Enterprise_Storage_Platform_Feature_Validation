# 1.3 — Array Architecture

## Objective

Understand the major architectural components of an enterprise storage array, how the host-facing and storage-facing sides are connected, how controllers and cache participate in I/O, and how controller redundancy works through active/active, active/passive, ownership, failover, and failback.

---

# 1.3 Architecture Overview

A generic dual-controller enterprise storage array can be visualized as:

```text
                         ENTERPRISE STORAGE ARRAY

        Host / Storage Network
                  │
          ┌───────┴────────┐
          ↓                ↓
   Front-End Port A   Front-End Port B
          ↓                ↓
     ┌──────────┐      ┌──────────┐
     │Controller│ ⇄⇄⇄  │Controller│
     │    A     │       │    B     │
     │  Cache   │       │  Cache   │
     └────┬─────┘       └────┬─────┘
          │                  │
          ↓                  ↓
     Back-End Port      Back-End Port
          │                  │
          └────────┬─────────┘
                   ↓
          Drive Enclosure(s)
                   ↓
            Physical Drives
```

A separate management path may exist:

```text
Engineer Laptop
       ↓
Management Network
       ↓
Array Management Interface
```

> The exact physical layout, controller design, port types, internal mappings, and redundancy mechanisms vary by storage vendor and product. This architecture is a learning model representing common enterprise-array concepts.

---

# 1. Front-End Ports

## Definition

A **front-end port** is an array-side interface used for **host-facing storage connectivity**.

Conceptually:

```text
Host
  ↓
Storage Network / Direct Connectivity
  ↓
Front-End Port
  ↓
Controller
```

Depending on the array, front-end connectivity may use technologies such as:

```text
Fibre Channel
iSCSI
Ethernet-based storage connectivity
SAS
```

The exact technology is platform-specific.

## Role

The front-end port provides the entry point for host storage traffic into the array.

For example:

```text
Host
  ↓
FC
  ↓
Array Front-End Port
  ↓
Controller
```

## Important distinction

```text
Front-End Port
= Host-facing array connectivity
```

It is not the controller itself.

```text
Front-End Port
     ↓
connectivity

Controller
     ↓
storage I/O processing
```

---

# 2. Back-End Ports

## Definition

A **back-end port** is an array-side interface used for connectivity toward the array's underlying storage resources, such as drive enclosures and physical drives.

Conceptually:

```text
Controller
    ↓
Back-End Port
    ↓
Drive Enclosure
    ↓
Physical Drives
```

A common example is controller-to-expansion-enclosure SAS connectivity, although the exact backend technology depends on the storage platform.

## Role

The backend provides the storage-facing connectivity needed to carry the operations generated by the array toward the underlying storage.

Example:

```text
Controller
    ↓
Back-End
    ↓
Drive Enclosure
    ↓
SSD / HDD
```

## Front-End vs Back-End

```text
FRONT-END
    ↓
Host-facing

BACK-END
    ↓
Storage-facing
```

This distinction should become automatic when looking at an array architecture.

---

# 3. Controllers

## Definition

A **storage controller** is the array component that receives, processes, and coordinates storage I/O between the host-facing side and the underlying storage side.

Conceptually:

```text
Host
  ↓
Front-End
  ↓
Controller
  ↓
Back-End
  ↓
Storage
```

The controller is therefore an important processing boundary:

```text
Host-visible logical I/O
          ↓
      Controller
          ↓
Array-side storage operations
```

## Controller processing

For a request such as:

```text
WRITE
LUN 10
LBA 1000
Length = N blocks
```

the controller conceptually:

```text
Receives the request
      ↓
Resolves / validates the logical storage access
      ↓
Processes it according to the array architecture
      ↓
Coordinates the required backend storage operation
```

The exact internal implementation is vendor-specific.

---

# 4. Multiple Controllers

Enterprise arrays commonly use multiple controllers to provide redundancy and continued storage availability.

A simplified architecture is:

```text
              Controller A
             ┌────────────┐
Host ───────→│            │
             └────────────┘

             Controller B
             ┌────────────┐
Host ───────→│            │
             └────────────┘
```

The important reason for multiple controllers is that a single controller should not unnecessarily become a single point of failure.

However:

```text
Two Controllers
≠
Automatically Active/Active
```

The actual controller operating model depends on the platform.

---

# 5. Controller Cache

## Definition

Controller cache is high-speed memory associated with the controller that can temporarily hold and manage I/O data and/or metadata while the array processes storage operations.

Conceptually:

```text
Front-End
    ↓
Controller
    ↓
Cache
    ↓
Backend Processing
    ↓
Drives
```

Cache is temporary working storage, not the final persistent storage.

```text
Cache
≠
Physical Storage
```

---

## Write Cache

For a write:

```text
Host WRITE
     ↓
Controller
     ↓
Cache
     ↓
Backend Storage
```

The array can use cache to absorb and manage incoming writes while coordinating backend storage operations.

Enterprise arrays use protected-cache mechanisms when cached data must survive relevant power/controller failure scenarios.

Possible protection mechanisms are platform-specific, such as:

```text
Battery-backed designs
Supercapacitor-backed designs
Nonvolatile / flash-backed mechanisms
Other vendor-specific protection
```

Therefore:

```text
Write entered cache
≠
Universal guarantee that the write is already on physical media
```

The exact host acknowledgement behavior depends on the array's cache and write policy.

---

## Read Cache

For a read:

```text
Host READ
    ↓
Controller
    ↓
Check cache
```

Two conceptual outcomes exist:

### Cache Hit

```text
READ
 ↓
Cache Hit
 ↓
Data returned
```

The backend drive may not need to be accessed for that read.

### Cache Miss

```text
READ
 ↓
Cache Miss
 ↓
Backend Read
 ↓
Drive
 ↓
Data returned
```

---

# 6. Data Path

## Definition

The **data path** is the route through which actual storage I/O travels between the host and the physical storage.

Array-side view:

```text
Host
  ↓
Front-End
  ↓
Controller
  ↓
Cache / Internal Processing
  ↓
Back-End
  ↓
Drive Enclosure
  ↓
Drive
```

Combined with the host-side path:

```text
Application
   ↓
Filesystem
   ↓
OS / Kernel
   ↓
Block Layer
   ↓
Driver / Multipath
   ↓
Storage Protocol
   ↓
Front-End Port
   ↓
Controller
   ↓
Cache / Internal Processing
   ↓
RAID / Pool / Logical Mapping
   ↓
Back-End
   ↓
Drive
```

---

# 7. WRITE Data Path

Example request:

```text
WRITE
LUN 10
LBA 1000
Length = N blocks
Data
```

Conceptual flow:

```text
Application
    ↓
Filesystem
    ↓
Block Layer
    ↓
Driver / Multipath
    ↓
Storage Protocol
    ↓
Front-End Port
    ↓
Controller
    ↓
Cache / Internal Processing
    ↓
RAID / Pool / Logical Mapping
    ↓
Back-End
    ↓
Drive
```

Important concept:

```text
One host I/O
      ↓
may become
multiple backend operations
```

For example, protection schemes such as mirroring or parity can require more than one backend operation.

The exact algorithm depends on the storage implementation.

---

# 8. READ Data Path

Example:

```text
READ
LUN 10
LBA 1000
Length = N blocks
```

Conceptually:

```text
Host
  ↓
Front-End
  ↓
Controller
  ↓
Cache?
```

If the data is available in cache:

```text
Cache Hit
   ↓
Data returned
   ↓
Host
```

If not:

```text
Cache Miss
   ↓
Back-End
   ↓
Drive
   ↓
Data returned
   ↓
Controller
   ↓
Front-End
   ↓
Host
```

---

# 9. Management Path

## Definition

The **management path** is the communication path used by administrators/engineers to configure, monitor, and manage the storage system.

Conceptually:

```text
Engineer Laptop
      ↓
Management Network
      ↓
Array Management Interface
      ↓
Storage System
```

Possible management methods include:

```text
GUI
CLI
SSH
HTTPS / APIs
```

depending on the platform.

---

# 10. Data Path vs Management Path

This distinction is critical.

## Data Path

Carries actual storage I/O:

```text
Application
    ↓
Host Storage Stack
    ↓
Storage Protocol
    ↓
Array
    ↓
Physical Storage
```

## Management Path

Carries administrative/control traffic:

```text
Engineer Laptop
       ↓
Management Network
       ↓
Management Interface
       ↓
Array
```

Therefore:

```text
DATA PATH
= actual storage I/O

MANAGEMENT PATH
= configure / monitor / administer
```

### Important real-world example

An engineer can:

```text
Laptop
  ↓
SSH
  ↓
Validation Host
  ↓
Start FIO
```

The SSH connection itself is **not carrying the FIO storage I/O**.

FIO runs on the validation host, and the storage I/O follows that host's storage path.

---

# 11. Active / Active

## Definition

In an **Active/Active** architecture, multiple controllers can actively participate in servicing storage workloads according to the platform's architecture.

Conceptually:

```text
             Controller A
Host ───────→   ACTIVE
                 
             Controller B
Host ───────→   ACTIVE
```

Both controllers are capable of actively participating.

However:

```text
Active/Active
≠
Every LUN must be serviced identically through both controllers at all times
```

A particular logical resource can still have preferred/optimized servicing relationships depending on the array architecture.

For example:

```text
LUN 10 → Controller A preferred
LUN 20 → Controller B preferred
```

while both controllers are active in the overall system.

---

# 12. Active / Passive

## Definition

In an **Active/Passive** architecture, a particular logical storage resource normally has one active servicing controller/path while another controller/path is available as the alternate/takeover side.

Conceptually:

```text
Controller A
    ↓
  ACTIVE
    ↓
 LUN 10

Controller B
    ↓
 PASSIVE / ALTERNATE
```

The passive controller can remain powered and healthy.

```text
PASSIVE
≠
POWERED OFF
```

It means the controller is not normally servicing that logical resource in the same active role.

---

# 13. Active / Active vs Active / Passive

```text
Active / Active
→ Multiple controllers can actively participate in servicing workloads.

Active / Passive
→ A particular logical resource normally has an active servicing side
  and an alternate takeover side.
```

The exact behavior is platform-specific.

---

# 14. Ownership

## Definition

**Ownership** is the relationship by which a storage array associates a logical storage resource with a controller responsible for servicing it under the normal/current operating model.

Example:

```text
Controller A
     ↓
   LUN 10
```

This can be expressed as:

```text
Controller A owns LUN 10
```

Meaning:

> Controller A is the controller associated with servicing LUN 10 under the array's normal operating model.

---

## Ownership is not physical possession

Ownership does not mean:

```text
Controller A physically owns Drive 7
```

Rather:

```text
LUN / Logical Resource
          ↓
Controller ownership / servicing relationship
```

A second controller can still have an available path to the same logical storage resource.

---

# 15. Ownership and Multipath

These concepts are related but different.

### Ownership

```text
Array side
   ↓
Which controller is associated with servicing the logical resource?
```

### Multipath

```text
Host side
   ↓
Which available storage path should be used?
```

Example:

```text
Host
 ├── Path 1 → Controller A
 └── Path 2 → Controller B

LUN 10
Owner / Preferred Controller → A
```

The array-side ownership relationship and host-side multipath path selection interact, but they are not the same concept.

---

# 16. Failover

## Definition

**Failover** is the transition of storage service for a logical resource from an unavailable controller/path to an available alternate controller/path according to the array and host multipathing architecture.

Normal:

```text
LUN 10
   ↓
Controller A
```

Failure:

```text
Controller A
     X
```

Failover:

```text
LUN 10
   ↓
Controller B
```

---

# 17. Controller Failover Sequence

A simplified sequence is:

```text
Controller A fails
        ↓
Array detects failure
        ↓
Logical resource/service responsibility transitions
        ↓
Controller B becomes the servicing side
        ↓
Host path state changes
        ↓
Multipath detects the failed path
        ↓
Multipath selects surviving path
        ↓
I/O continues / recovers according to the platform
```

Important:

```text
Controller failover
≠
Path failover
```

They can occur together but are different events.

---

## Controller Failure

```text
Controller A
     X
     ↓
Controller B services LUN
```

## Path Failure

```text
Path 1
  X

Path 2
  ↓
continues carrying I/O
```

A path can fail while both controllers remain healthy.

---

# 18. What Happens to In-Flight I/O?

If a controller fails while I/O is outstanding, the result is platform- and timing-dependent.

Possible observations can include:

```text
Transient I/O errors
Retries
Path failure
Path recovery
Continued I/O
Temporary latency increase
Application-visible interruption
```

A validation engineer must compare the observed behavior against the documented requirement.

Do not assume:

```text
Controller failure
→ every I/O must immediately succeed
```

or:

```text
Controller failure
→ every I/O must fail
```

The actual behavior must be tested.

---

# 19. Failover and Cache

If the failed controller had outstanding cached data:

```text
Host WRITE
     ↓
Controller A
     ↓
Protected Cache
     ↓
Controller A fails
```

the array must have a defined mechanism for protecting and recovering that cached state.

Possible mechanisms include:

```text
Cache mirroring
Protected / nonvolatile cache
Recovery and destaging
Controller coordination
```

The exact mechanism is vendor-specific.

---

# 20. Failback

## Definition

**Failback** is the process of returning storage service toward the preferred/original controller or path after the failure condition has been resolved, according to the array and host configuration.

Timeline:

```text
NORMAL
LUN 10 → Controller A
        ↓
Controller A fails
        ↓
FAILOVER
LUN 10 → Controller B
        ↓
Controller A recovers
        ↓
FAILBACK
        ↓
Preferred / normal servicing state
```

---

# 21. Controller Recovery Does Not Automatically Prove Failback

Suppose:

```text
Controller A = Healthy
Controller B = currently servicing LUN 10
```

The fact that Controller A is powered on and healthy does not by itself prove:

```text
LUN 10 → Controller A
```

The platform may have configuration/policy determining whether service returns automatically, remains on the surviving controller, or requires another action.

Therefore, validation must verify the **actual post-recovery state**.

---

# 22. Failover vs Failback

```text
FAILOVER

Normal Controller
       ↓
Failure
       ↓
Alternate Controller
```

```text
FAILBACK

Alternate Controller
       ↓
Original / Preferred Controller Recovers
       ↓
Preferred / Normal State
```

Both behaviors should be validated where required.

---

# 23. Real Validation Scenario

A storage-validation test for controller redundancy can conceptually be:

```text
Verify both controllers healthy
        ↓
Verify redundant host paths
        ↓
Verify LUN accessibility
        ↓
Start continuous I/O
        ↓
Inject controller failure
        ↓
Observe controller state
        ↓
Observe LUN servicing/ownership
        ↓
Observe host path state
        ↓
Observe multipath behavior
        ↓
Observe application/FIO behavior
        ↓
Restore failed controller
        ↓
Observe recovery
        ↓
Verify expected failback/path state
        ↓
Verify data and I/O correctness
```

# 24. Troubleshooting / RCA Perspective

A storage failure should be isolated by layer.

Example:

```text
Host
 ↓
Path
 ↓
Front-End
 ↓
Controller
 ↓
Cache
 ↓
Back-End
 ↓
Drive
```

Possible observations:

### Management failure

```text
Array GUI unavailable
```

while:

```text
Storage I/O continues
```

This points toward the management path rather than automatically indicating a data-path failure.

### Data-path failure

```text
Array GUI works
```

but:

```text
Host I/O fails
```

This requires investigation of the storage data path.

### Controller failure

```text
Front-End connectivity
      ↓
Controller failure
      ↓
Failover
```

### Backend failure

```text
Controller healthy
      ↓
Backend connectivity/storage issue
      ↓
RAID / Pool / Drive investigation
```

The key RCA principle is:

> **Identify the failing layer instead of calling every failure a generic “storage issue.”**

# 26. Key Definitions

| Component / Concept | Meaning                                                                                 |
| ------------------- | --------------------------------------------------------------------------------------- |
| Front-End Port      | Array-side host-facing storage interface                                                |
| Back-End Port       | Array-side storage-facing interface toward backend storage                              |
| Controller          | Processes and coordinates storage I/O                                                   |
| Cache               | Temporary high-speed memory used for I/O data and/or metadata                           |
| Data Path           | Path carrying actual storage I/O                                                        |
| Management Path     | Path used for administration, monitoring, and configuration                             |
| Active/Active       | Multiple controllers can actively participate in servicing workloads                    |
| Active/Passive      | A logical resource normally has an active servicing side and an alternate takeover side |
| Ownership           | Controller relationship associated with servicing a logical storage resource            |
| Failover            | Service transition from unavailable controller/path to an available alternate           |
| Failback            | Return toward the preferred/original servicing state after recovery                     |
