# RAID 50

## 1. Overview

RAID 50 combines:

* RAID 5
* RAID 0

Its fundamental design is:

```text
Multiple RAID 5 Groups
          ↓
       RAID 0
          ↓
       RAID 50
```

The purpose of RAID 50 is to combine:

```text
RAID 5
→ Parity-based protection

RAID 0
→ Striping across RAID 5 groups
```

The resulting architecture provides:

```text
Data protection
+
Parallel I/O
+
Higher aggregate capacity
```

RAID 50 does not create one large RAID 5 parity domain.

Instead, it creates multiple independent RAID 5 component arrays and stripes
logical data across them.

---

# 2. Why RAID 50 Exists

A single RAID 5 group provides:

```text
Striping
+
Distributed parity
+
Single-member fault tolerance
```

However, large RAID 5 configurations can have:

```text
More members
+
Larger rebuild scope
+
More drives participating in parity operations
```

RAID 50 addresses this by dividing the drives into multiple RAID 5 groups.

Conceptually:

```text
RAID 5 Group 1
        +
RAID 5 Group 2
        +
RAID 5 Group 3
        ↓
     RAID 0
```

This creates a striped set of protected RAID 5 groups.

---

# 3. RAID 50 Architecture

The general RAID 50 architecture is:

```text
                         RAID 50
                            |
                       RAID 0 layer
                     /      |      \
                    /       |       \
                 RAID 5   RAID 5   RAID 5
                 Group 1  Group 2  Group 3
```

For the laboratory configuration, two RAID 5 groups were used:

```text
                  md50
                 RAID 0
                /      \
              md51     md52
             RAID 5    RAID 5
            /  |  \    /  |  \
         D1  D2  D3  D4  D5  D6
```

The Linux `mdadm` hierarchy was:

```text
md50 → top-level RAID 0
md51 → component RAID 5
md52 → component RAID 5
```

The original laboratory members were:

```text
md51:
loop10
loop11
loop12

md52:
loop13
loop14
loop15
```

Replacement devices were introduced during the failure and recovery tests.

---

# 4. RAID 50 Data Protection Model

Each RAID 5 component provides its own parity protection.

For a RAID 5 group:

```text
Data + distributed parity
```

Conceptually:

```text
D1   D2   Parity
D3   Parity D4
Parity D5   D6
```

The exact parity location rotates across the members.

RAID 50 then stripes logical data across multiple RAID 5 groups:

```text
               RAID 0
          /               \
       RAID 5             RAID 5
        md51               md52
```

Therefore protection is applied independently inside each component
RAID 5 group.

---

# 5. The Most Important RAID 50 Rule

The most important RAID 50 engineering rule is:

> **Failure tolerance must be evaluated independently for every RAID 5 component group.**

For example:

```text
md51 → 1 failed
md52 → 1 failed
```

Both groups remain operational.

Therefore:

```text
md50 → operational
```

But:

```text
md51 → 2 failed
md52 → 0 failed
```

causes the RAID 5 protection of `md51` to be exceeded.

Then:

```text
md51 → unavailable
       ↓
md50 loses one RAID 0 component
       ↓
RAID 50 becomes unavailable
```

Failure distribution is therefore more important than total failure count alone.

---

# 6. RAID 50 Redundancy Mechanism

RAID 50 uses two different mechanisms:

```text
RAID 5
→ Parity-based redundancy

RAID 0
→ Striping
```

Conceptually:

```text
Physical members
      ↓
RAID 5 groups
      ↓
Data + parity
      ↓
RAID 0 striping
      ↓
Logical RAID 50
```

The redundancy is not provided by the top-level RAID 0.

The top-level RAID 0 only distributes data across the protected RAID 5
components.

---

# 7. RAID 50 Read Path

A logical read is presented to the RAID 50 layer.

Conceptually:

```text
Host
 ↓
RAID 50
 ↓
RAID 0 layer
 ↓
Target RAID 5 group
 ↓
Available RAID 5 members
 ↓
Requested data
```

Depending on the logical address, the RAID 0 layer selects the appropriate
component RAID 5 array.

The RAID 5 layer then services the request from its members.

For a normal healthy read, parity calculation is not required merely to read
existing data.

---

# 8. RAID 50 Write Path

A logical write first enters the top-level RAID 0 layer.

Conceptually:

```text
Host
 ↓
RAID 50
 ↓
RAID 0
 ↓
Selected RAID 5 group
 ↓
Data + parity maintenance
 ↓
RAID 5 members
```

The selected RAID 5 component performs the required data and parity updates.

Therefore the write path contains parity-maintenance work inside the affected
RAID 5 group.

The top-level RAID 0 layer does not calculate parity.

---

# 9. RAID 50 Parity

Each RAID 5 component maintains its own parity.

For a simple parity relationship:

```text
P = D1 XOR D2 XOR D3
```

Conceptually, if one member is unavailable:

```text
Missing Data
     =
Parity XOR
remaining Data
```

RAID 50 therefore inherits RAID 5's single-member fault tolerance per
component group.

There is no parity relationship between different RAID 5 component arrays.

For example:

```text
md51 parity
```

cannot reconstruct:

```text
md52 data
```

because they are independent RAID 5 groups.

---

# 10. RAID 50 Capacity

For equal-sized members, a simplified capacity model is:

```text
Usable Capacity
≈
Number of RAID 5 groups
×
(Group Members - 1)
×
Member Size
```

For example, with:

```text
2 RAID 5 groups
3 members per group
1 GiB member size
```

each RAID 5 group provides approximately:

```text
(3 - 1) × 1 GiB
=
2 GiB
```

Two groups provide approximately:

```text
2 GiB + 2 GiB
=
4 GiB
```

The laboratory top-level RAID 50 reported approximately:

```text
3.99 GiB
```

because of RAID metadata and filesystem/storage geometry.

---

# 11. Minimum Member Count

The minimum number of physical members depends on the number of component
RAID 5 groups and the implementation.

A practical RAID 50 design requires:

```text
At least two RAID 5 groups
```

and each RAID 5 group requires at least:

```text
3 members
```

Therefore a conventional two-group RAID 50 requires at least:

```text
6 members
```

Conceptually:

```text
Group 1 → D1 D2 D3
Group 2 → D4 D5 D6
```

---

# 12. RAID 50 Single-Member Failure

Suppose:

```text
md51:
D1 → FAILED
D2 → HEALTHY
D3 → HEALTHY
```

Then:

```text
md51 → [_UU]
```

The RAID 5 group is degraded but still operational.

If:

```text
md52 → [UUU]
```

then:

```text
md50 → operational
```

The RAID 50 filesystem can therefore remain accessible.

Conceptually:

```text
D1 ❌
D2 ✅
D3 ✅

RAID 5 continues using
remaining members + parity reconstruction
```

---

# 13. Single-Member Failure in Each RAID 5 Group

Consider:

```text
md51 → [_UU]
md52 → [_UU]
```

There is one failed member in each component RAID 5 group.

Each RAID 5 group still has enough members to operate.

Therefore:

```text
md51 → operational
md52 → operational
md50 → operational
```

This is an important RAID 50 distributed-failure pattern.

The failures are independent because each occurs inside a different RAID 5
protection domain.

---

# 14. Two-Member Failure in the Same RAID 5 Group

This is the critical failure scenario.

Suppose:

```text
md51:
D1 → FAILED
D2 → FAILED
D3 → HEALTHY
```

The component becomes:

```text
md51 → [__U]
```

RAID 5 can normally tolerate only one failed member in that component.

Therefore its protection has been exceeded.

The top-level RAID 0 requires every component array to remain available.

Thus:

```text
md51 failure
      ↓
RAID 0 loses md51
      ↓
RAID 50 becomes unavailable
```

The healthy `md52` cannot rebuild `md51`.

This is because:

```text
md51
```

and:

```text
md52
```

are independent RAID 5 protection domains.

---

# 15. Two-Member Failure in Different RAID 5 Groups

Now consider:

```text
md51:
D1 → FAILED
D2 → HEALTHY
D3 → HEALTHY

md52:
D4 → FAILED
D5 → HEALTHY
D6 → HEALTHY
```

The state is:

```text
md51 → [_UU]
md52 → [_UU]
```

Both RAID 5 groups are degraded.

However:

```text
md51 → still operational
md52 → still operational
```

Therefore:

```text
md50 → operational
```

This is the fundamental RAID 50 distributed-failure scenario.

---

# 16. RAID 50 Failure Matrix

For a two-component RAID 50:

| Failure Pattern | md51     | md52     | RAID 50     |
| --------------- | -------- | -------- | ----------- |
| 0 + 0           | Healthy  | Healthy  | Operational |
| 1 + 0           | Degraded | Healthy  | Operational |
| 0 + 1           | Healthy  | Degraded | Operational |
| 1 + 1           | Degraded | Degraded | Operational |
| 2 + 0           | Failed   | Healthy  | Unavailable |
| 0 + 2           | Healthy  | Failed   | Unavailable |

The important rule is:

```text
Every RAID 5 component must remain operational.
```

---

# 17. Failure Count vs Failure Distribution

A RAID 50 failure must never be evaluated using only:

```text
Total failed drives
```

For example:

```text
2 failed drives
```

could mean:

```text
1 in md51
+
1 in md52
```

which can remain operational.

Or:

```text
2 in md51
+
0 in md52
```

which can cause RAID 50 failure.

Therefore the correct engineering question is:

> **How are the failed members distributed across the RAID 5 component groups?**

---

# 18. Degraded-State Validation

After a member failure, always verify:

```bash
cat /proc/mdstat
```

Then inspect the affected RAID 5 group:

```bash
sudo mdadm --detail /dev/md51
```

or:

```bash
sudo mdadm --detail /dev/md52
```

Then inspect the top-level RAID 50:

```bash
sudo mdadm --detail /dev/md50
```

Important fields include:

```text
State
Active Devices
Working Devices
Failed Devices
Spare Devices
Raid Devices
Raid Level
Layout
Chunk Size
```

---

# 19. Data Accessibility During Degraded Mode

A degraded RAID status should be followed by filesystem validation.

Check the mount:

```bash
mount | grep /mnt/raid50
```

Check the directory:

```bash
ls -lh /mnt/raid50
```

Read a test file:

```bash
cat /mnt/raid50/testfile_01.txt
```

A complete validation chain is:

```text
RAID degraded
      ↓
Component still operational
      ↓
md50 still active
      ↓
Filesystem mounted
      ↓
Files readable
```

---

# 20. Data Integrity Validation

File readability alone is not enough.

Create a healthy-state checksum baseline:

```bash
sha256sum /mnt/raid50/testfile_01.txt \
          /mnt/raid50/testfile_02.txt \
          /mnt/raid50/testfile_03.txt
```

Then repeat the same checksum validation:

```text
After failure
After rebuild
After final recovery
```

The expected result is that the hashes remain identical.

The laboratory baseline was:

```text
testfile_01.txt
7c30f4d66983818b9321e763f347f821b28ab5c1e8f8b496dfc4af2cd838c4a0

testfile_02.txt
ef08c205487d8ea98e6fc1985427707df9790506452612eb0bacfbd904d90072

testfile_03.txt
bde5543759a5c299223c09fe593a87cf460329861b31273ff29cd38a7811e7c1
```

---

# 21. RAID 50 Rebuild

A failed member is rebuilt inside its component RAID 5 array.

Suppose:

```text
md51 → [_UU]
```

and a replacement member is available.

The recovery process is:

```text
Failed member
      ↓
Remove failed member
      ↓
Add replacement
      ↓
RAID 5 reconstruction
      ↓
Rebuild replacement
      ↓
md51 returns to healthy state
```

The top-level RAID 50 device:

```text
md50
```

does not perform an independent parity rebuild for the physical member.

The recovery takes place inside:

```text
md51
```

or:

```text
md52
```

---

# 22. Replacement Member Validation

Before adding a replacement member, verify that it does not contain stale
RAID metadata.

Example:

```bash
sudo mdadm --examine /dev/loopX
```

A clean replacement should report:

```text
mdadm: No md superblock detected on /dev/loopX.
```

Then add it to the appropriate RAID 5 component:

```bash
sudo mdadm --manage /dev/md51 --add /dev/loopX
```

or:

```bash
sudo mdadm --manage /dev/md52 --add /dev/loopX
```

---

# 23. Monitoring Rebuild

Monitor recovery using:

```bash
cat /proc/mdstat
```

or:

```bash
watch -n 2 cat /proc/mdstat
```

Typical recovery output includes:

```text
recovery = XX.X%
```

The important point is to continue monitoring until the affected RAID 5
returns to a healthy state.

Conceptually:

```text
[_UU]
  ↓
Rebuild
  ↓
[UUU]
```

---

# 24. Rebuild Completion

A rebuild is not complete merely because it started.

Verify:

```bash
cat /proc/mdstat
```

Then:

```bash
sudo mdadm --detail /dev/md51
```

or:

```bash
sudo mdadm --detail /dev/md52
```

Expected healthy condition:

```text
State             : clean
Active Devices    : 3
Working Devices   : 3
Failed Devices    : 0
```

Then verify the top-level RAID 50:

```bash
sudo mdadm --detail /dev/md50
```

Finally verify data integrity with:

```bash
sha256sum /mnt/raid50/testfile_01.txt \
          /mnt/raid50/testfile_02.txt \
          /mnt/raid50/testfile_03.txt
```

---

# 25. Rebuild Window

During a RAID 5 component rebuild:

```text
Normal application I/O
        +
Reads from surviving members
        +
Parity/data reconstruction
        +
Writes to replacement
```

Therefore rebuild can increase storage workload.

Potential effects include:

```text
Higher latency
Lower throughput
Higher disk activity
Longer I/O completion times
```

The exact impact depends on the storage platform, workload, RAID implementation,
and rebuild policy.

---

# 26. Failure During Rebuild

Suppose:

```text
md51 → [_UU]
```

and a replacement member is rebuilding.

If another member of `md51` fails during the rebuild:

```text
md51 → [__U]
```

the RAID 5 component has lost its single-member protection boundary.

The consequence is:

```text
md51 unavailable
      ↓
md50 loses one component
      ↓
RAID 50 becomes unavailable
```

Therefore RAID 50 rebuild windows require careful monitoring.

---

# 27. Distributed Failure During Rebuild

Consider:

```text
md51 → [_UU]
md52 → [_UU]
```

Both components are already degraded.

If `md51` is rebuilding and another member of `md51` fails:

```text
md51 → [__U]
```

the RAID 5 group becomes unavailable even though `md52` may still be healthy
or degraded.

This demonstrates the importance of:

```text
Failure location
+
Rebuild state
+
Component RAID health
```

---

# 28. Filesystem Troubleshooting

If RAID metadata appears healthy but the filesystem is inaccessible, separate
the problem into layers:

```text
Physical member
      ↓
RAID 5 component
      ↓
RAID 0 layer
      ↓
/dev/md50
      ↓
Filesystem
      ↓
Mount
      ↓
Application
```

Useful commands include:

```bash
lsblk -f
```

```bash
mount | grep /mnt/raid50
```

```bash
df -h /mnt/raid50
```

Do not immediately classify every filesystem problem as a RAID problem.

A healthy RAID stack can still have:

```text
Filesystem corruption
Mount failure
Permission problems
Application problems
```

---

# 29. RAID 50 Physical Disk Identification

Never replace a physical device based only on a device name such as:

```text
/dev/sdb
/dev/sdc
```

For real hardware, verify:

```text
Drive serial number
Drive model
Physical slot
Operating-system device path
RAID membership
RAID component group
```

The important hierarchy is:

```text
Physical Disk
      ↓
RAID 5 component
      ↓
RAID 0 component
      ↓
RAID 50
```

For troubleshooting, determine exactly which component array contains the
failed member.

# 31. RAID 50 Operational State Model

A useful engineering model is:

```text
                    RAID 50
                       |
                    RAID 0
                 /           \
                /             \
             RAID 5          RAID 5
              md51            md52
             [UUU]            [UUU]
```

Healthy state:

```text
md51 → [UUU]
md52 → [UUU]
```

One distributed failure:

```text
md51 → [_UU]
md52 → [UUU]
```

Two distributed failures:

```text
md51 → [_UU]
md52 → [_UU]
```

Still operational because both component arrays remain available.

But:

```text
md51 → [__U]
```

means the RAID 5 component has exceeded its protection boundary.

Therefore:

```text
md51 unavailable
      ↓
md50 unavailable
      ↓
RAID 50 unavailable
```

---

# 32. RAID 50 vs RAID 5

| Feature                   | RAID 5                 | RAID 50                                                             |
| ------------------------- | ---------------------- | ------------------------------------------------------------------- |
| Basic structure           | Single RAID 5 group    | Multiple RAID 5 groups striped by RAID 0                            |
| Redundancy                | Distributed parity     | Distributed parity inside each component                            |
| Top-level striping        | RAID 5 striping        | RAID 0 across RAID 5 groups                                         |
| Single-member failure     | Normally tolerated     | Normally tolerated per component                                    |
| Two-member failure        | Normally not tolerated | Can be tolerated when distributed across different component groups |
| Same-group double failure | Array unavailable      | Affected RAID 5 component unavailable                               |
| Failure domain            | Entire RAID 5          | Individual RAID 5 component                                         |
| Capacity efficiency       | `(N-1) × size`         | Sum of each RAID 5 group's usable capacity                          |

---

# 33. RAID 50 vs RAID 6

| Feature                     | RAID 6                                   | RAID 50                                         |
| --------------------------- | ---------------------------------------- | ----------------------------------------------- |
| Redundancy                  | P + Q                                    | Multiple RAID 5 groups                          |
| Two-member protection       | Within one RAID 6 group                  | One failure per RAID 5 component                |
| Parity model                | Dual parity                              | Single parity per component                     |
| Failure domain              | Whole RAID 6 group                       | Individual RAID 5 component                     |
| Distributed failures        | Two within same group normally tolerated | Can tolerate one per component                  |
| Same-component two failures | Normally tolerated                       | Exceeds RAID 5 protection                       |
| Rebuild                     | P/Q reconstruction                       | RAID 5 reconstruction within affected component |

The failure models are therefore fundamentally different.

---

# 34. RAID 50 vs RAID 10

| Feature               | RAID 10                     | RAID 50                                     |
| --------------------- | --------------------------- | ------------------------------------------- |
| Redundancy            | Mirroring                   | Parity                                      |
| Striping              | Across mirror groups        | Across RAID 5 groups                        |
| Parity                | No                          | Yes                                         |
| Usable capacity       | Approximately 50%           | Higher than RAID 10 for many configurations |
| Single-member failure | Normally tolerated          | Normally tolerated per RAID 5 component     |
| Rebuild               | Mirror-copy based           | Parity reconstruction                       |
| Multiple failures     | Depends on mirror placement | Depends on RAID 5 component placement       |
| Small-write behavior  | No parity maintenance       | RAID 5 parity maintenance                   |

---

# 35. RAID 50 Troubleshooting Decision Process

Use this sequence:

```text
RAID problem
    ↓
cat /proc/mdstat
    ↓
Identify md50
    ↓
Identify md51 / md52
    ↓
Identify failed physical member
    ↓
Map member to RAID 5 component
    ↓
Count failures inside that component
    ↓
Is the RAID 5 component operational?
    ↓
YES
 ↓
Verify md50
 ↓
Verify filesystem
 ↓
Verify data integrity
 ↓
Rebuild
```

If:

```text
RAID 5 component unavailable
```

then:

```text
RAID 0 loses a required component
        ↓
RAID 50 unavailable
```

```text

      ↓
Verify RAID metadata
      ↓
Create filesystem
      ↓
Mount filesystem
      ↓
Write test data
      ↓

      ↓

      ↓

      ↓

      ↓

      ↓

      ↓
```

This validates both:

```text

+

```

# 38. Final RAID 50 Mental Model

Think about RAID 50 as:

```text
               RAID 50
                  |
               RAID 0
              /      \
             /        \
          RAID 5     RAID 5
           md51       md52
          / | \      / | \
         D  D  D    D  D  D
```

For every failure:

```text
Failed Disk
     ↓
Which RAID 5 group?
     ↓
How many failures in that group?
     ↓
Is that RAID 5 still operational?
```

If yes:

```text
Component survives
       ↓
RAID 50 can remain operational
```

If no:

```text
Component RAID 5 fails
       ↓
RAID 0 loses a required component
       ↓
RAID 50 becomes unavailable
```

---

# 39. Key Engineering Takeaways

1. RAID 50 combines multiple RAID 5 groups with RAID 0 striping.
2. The top-level RAID 0 provides striping but no redundancy.
3. Each RAID 5 component maintains its own parity protection.
4. RAID 50 does not have one global parity domain.
5. A single failed member is normally tolerated within a RAID 5 component.
6. One failed member in each of two RAID 5 groups can be survivable.
7. Two failures in the same RAID 5 component exceed that component's normal protection.
8. A failed RAID 5 component causes the top-level RAID 0 to lose a required component.
9. Failure distribution is therefore critical when troubleshooting RAID 50.
10. Rebuilds occur inside the affected RAID 5 component.
11. Rebuild activity should be monitored with `/proc/mdstat`.
12. Rebuild completion must be verified using `mdadm --detail`.
13. Filesystem accessibility should be validated independently from RAID health.
14. SHA-256 verification provides stronger evidence of data integrity than simply reading a file.
15. Replacement members should be checked for stale RAID metadata before being added.
16. Physical disk identity must be verified before replacing real hardware.
17. RAID 50 provides a different failure model from RAID 6 and RAID 10.
18. The key RAID 50 troubleshooting question is where the failure occurred, not only how many drives failed.

---

# 40. Final Engineering Principle

> **RAID 50 fault tolerance is determined per RAID 5 component group.**

The correct troubleshooting model is:

```text
Failed member
      ↓
Identify RAID 5 component
      ↓
Count failures inside that component
      ↓
Verify component RAID health
      ↓
Verify top-level RAID 0
      ↓
Verify filesystem
      ↓
Verify data integrity
      ↓
Rebuild
      ↓
Verify final redundancy
```

The central rule is:

```text
One failed member per RAID 5 component
→ component can remain operational

Two failed members in the same RAID 5 component
→ RAID 5 protection exceeded
→ RAID 50 becomes unavailable
```

Understanding this failure-domain model is the foundation for effectively
testing, troubleshooting, and validating RAID 50 in enterprise storage
environments.
